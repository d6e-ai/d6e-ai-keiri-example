# d6e AI 向け - シナリオ E 追記指示書 (Drive ミラー活用)

> **このファイルは d6e ワークスペースに直接登録するプロンプトではありません。**
> 内容を **全文そのままコピーして d6e のチャット UI に貼り付けてください**。
> 受け取った d6e AI が、次の MCP ツールを使ってシナリオ E を **対話的に具体化** し、
> 既存の `ai-keiri-prompt.md` 由来の prompt rule の **`## 共通ルール` 見出しの直前**
> (= シナリオ C / D の直後) にシナリオ E を **挿入** します。これによりタスク種別
> A/B/C/(D)/E が連続したセクションとして並び、共通ルールはその下にまとめて適用される
> 構造になります。
>
> - `d6e_list_workspace_prompt_rules` / `d6e_update_workspace_prompt_rule` — rule の取得と更新
> - `d6e_call_external_api` — Drive Sync ミラーの REST 経由ヘルスチェックを行うため
>   (`GET ${D6E_BASE_URL}/api/v1/drive-sync/status?workspace_id=<this workspace>`)
> - `d6e_sql` — `user_data.drive_files` 投影テーブルから「Drive ルート直下のフォルダ名」を
>   サンプリングし、`{{drive_root_hint}}` プレースホルダの具体化に使う
>
> 探索で確定した値はテンプレートの `{{drive_root_hint}}` を **置換** してから rule に
> 書き込みます。これにより、サンプルアプリ実行時の LLM は「このワークスペースの Drive
> ミラーには `経費レシート`、`契約書`、`請求書` といったフォルダがある」というヒント
> をすでに持った状態で動作し、検索クエリの組み立て精度が上がります。
>
> シナリオ E は **シナリオ A/B/C/D を一切変更せず**、Drive ミラー検索が必要なターン
> でだけ発動する **追加** のシナリオです。Drive Sync が未設定 / `drive_files` が空の
> 場合でもシナリオ A/B/C/D は壊れません (シナリオ E 自体がフォールバック節を持ちます)。

## d6e AI への作業指示

あなたはこのリクエストを受け取った d6e AI です。次の手順を **そのままの順番** で実行してください。
途中で曖昧な点があれば必ずユーザーに確認してから次のステップに進んでください。
作業対象のワークスペースは **このチャットが属するワークスペース** です (改めてユーザーに
`workspace_id` を質問する必要はありません)。

1. **既存ルールの取得**:
   - `d6e_list_workspace_prompt_rules` を呼び、現在のワークスペースに登録されている
     prompt rule 一覧を取得します。
2. **対象ルールの特定**:
   - 取得した一覧から、本文に `### シナリオ A: 仕訳作成` と `### シナリオ B: 仕訳修正` と
     `### シナリオ C: 一般経理質問` の **3 つの見出しがすべて含まれる rule** を 1 件特定します。
     これが本アプリの `ai-keiri-prompt.md` 由来の rule です。シナリオ D
     (`### シナリオ D: freee 仕訳登録 + Google Drive 領収書保存`) が同じ rule に
     既に追記されていても構いません。
   - 該当 rule が **見つからなかった場合**: 「ai-keiri-prompt.md 由来の prompt rule が
     見つかりません。先にサンプルアプリ側で `npm run init` を実行してください」と
     日本語で返答し、ここで処理を中断します。
   - **複数該当した場合**: ユーザーに該当 rule の `id` / `sort_order` / 先頭 200 文字を
     提示し、どの rule に追記すべきか確認してから次に進んでください。
3. **冪等性チェック**:
   - 特定した rule の `content` に既に `### シナリオ E: Drive ミラー検索からの仕訳提示`
     という見出しが含まれている場合は、追記は **行わず** に
     「対象 rule には既にシナリオ E が含まれているため、追記をスキップしました。
     Drive ヒントを更新したい場合は、d6e 管理画面の Prompt rules 画面でシナリオ E
     セクションを削除してからもう一度この指示書を貼り付けてください」と
     ユーザーに報告して終了してください。
4. **Drive Sync の有効化確認**:
   - `d6e_call_external_api` を `provider: "d6e_self"` の代わりに **直接 d6e REST** を
     呼べる手段で
     `GET ${D6E_BASE_URL}/api/v1/drive-sync/status?workspace_id=<このワークスペースの id>`
     を呼びます。d6e 標準の MCP に直接の HTTP ヘルパが無い場合は
     `d6e_sql` で `SELECT enabled, last_synced_at, last_sync_error FROM frontend.drive_sync_config WHERE workspace_id = …`
     を実行して状態を取得して構いません。
   - 取得結果が次のいずれかなら、ユーザーに案内して中断します:
     - `config` が存在しない、もしくは `enabled = false` → 「Drive Sync が未設定です。
       d6e の Files → Drive Sync または Settings → Integration から Google Drive 同期を
       有効化してから、再度この指示書を貼り付けてください」
     - `roots[]` が空 → 「Drive Sync が有効ですが、同期対象フォルダが未設定です。
       Drive Sync 設定で起点フォルダ (または共有ドライブ) を追加してから、再度この
       指示書を貼り付けてください」
   - 状態が良好なら次に進みます。`node_count` が 0 でも (まだ初回同期完了前でも)
     継続して構いませんが、その場合は手順 5 の SQL ヒント抽出をスキップし、
     `{{drive_root_hint}}` には日本語で「(初回同期未完了のため利用可能なフォルダは
     未取得。仕訳作成時に再度 SQL で確認してください)」を埋めます。
5. **Drive ヒントのサンプリング**:
   - `d6e_sql` で次のクエリを実行し、Drive ミラーのルート直下の上位フォルダ名を
     最大 5 件取得します:

     ```sql
     SELECT name, drive_id, path
     FROM drive_files
     WHERE is_folder = true
       AND (path LIKE '/%' AND path NOT LIKE '/%/%')
     ORDER BY name
     LIMIT 5;
     ```

     `drive_files` は `user_data.ws_<uuid>_drive_files` 投影テーブルへのワークスペース内
     エイリアスです (`d6e_sql` のセッション内では `drive_files` で参照できます)。

   - 結果が 0 件の場合は手順 4 の `node_count = 0` 時と同様に「(初回同期未完了のため
     利用可能なフォルダは未取得。仕訳作成時に再度 SQL で確認してください)」を埋めます。
   - 結果が得られたら、`name` を全角カンマ `、` で結合した文字列を `{{drive_root_hint}}`
     とします (例: `「経費レシート、契約書、請求書 2026、社内資料」`)。フォルダ名に
     クォートや改行が含まれる場合は除去してください。

6. **追記内容の具体化**:
   - 本書末尾の「追記する本文 (シナリオ E テンプレート)」をコピーし、次のプレース
     ホルダを **手順 5 で確定した値** に **すべて** 置換してください。
     - `{{drive_root_hint}}` — 上記で組み立てた文字列、または初回同期未完了時の
       フォールバック文言。
     - `{{generated_at}}` — d6e AI が手順 6 を実行した時刻 (ISO 8601、例:
       `2026-07-01T01:50:00+09:00`)。
   - 置換漏れが残らないよう、最終文字列に `{{` が含まれていないか必ず確認してください。
7. **追記内容の提示と確認**:
   - 具体化済みのシナリオ E 本文を **コードフェンスで囲んで** ユーザーに見せ、
     「以下の内容を rule (id=`<id>`) の **`## 共通ルール` 見出しの直前** に挿入します。
     よろしいですか？」と確認を取ります。挿入位置を明示的に伝えてください (末尾追記
     ではありません)。
   - ユーザーが了承したら次のステップに進みます。明確な拒否があれば中断してください。
8. **rule の更新 (挿入位置に注意)**:
   - 既存 `content` 内で見出し `## 共通ルール` の **行頭インデックス** を探します。
     見出し行はマークダウンの行頭が `## 共通ルール` で始まる行です。
   - 該当位置で `content` を 2 つに分割します:
     - `head` = 共通ルール見出しの直前までの文字列 (末尾の改行を含む)
     - `tail` = 共通ルール見出しから末尾までの文字列
   - 新しい `content` を次のように組み立てます:
     `head` + `（具体化済みシナリオ E 本文）` + `\n\n` + `tail`
     つまり「シナリオ A/B/C/(D) の **後**、共通ルールの **前**」に挿入します。
   - **フォールバック**: `## 共通ルール` 見出しが見つからない場合に限り、`content`
     末尾に `\n\n` 区切りで結合してください。その際は応答内で
     「`## 共通ルール` 見出しが検出できなかったため末尾に追記しました」と注意を残します。
   - `d6e_update_workspace_prompt_rule` を `rule_id` と新しい `content` で呼び出し、
     上書き保存します。`sort_order` は変更しません。
9. **完了報告**:
   - 「シナリオ E を rule (id=`<id>`) の (シナリオ D または C) の直後・共通ルールの
     直前に挿入しました。Drive ヒント=`{{drive_root_hint}}`。これ以降、ユーザーが
     `<drive_lookup_request>` タグ付きメッセージや『過去の領収書から探して』のような
     文面で依頼すると、LLM は `drive_files` を検索してから仕訳を提示します」と
     日本語で報告してください。

## ガードレール (必ず守る)

- **既存ルールの削除・置換を絶対に行わない**。`d6e_delete_workspace_prompt_rule` や
  `d6e_create_workspace_prompt_rule` をこの作業中に呼ばないでください (新規ルールでは
  なく既存 rule への追記が目的です)。
- **シナリオ A/B/C/D の本文を一切変更しない**。`content` の先頭から (シナリオ D が
  ある場合はその末尾まで、無い場合はシナリオ C の末尾まで) / `## 共通ルール` までの
  内容はそのまま保持してください。挿入はあくまで「最後のタスク種別シナリオと共通
  ルールの **境界** に新セクションを差し込む」操作です。前後のテキストの 1 文字も
  書き換えてはいけません。
- **このチャットのワークスペース以外の rule に触れない**。本作業で操作するのは現在の
  チャットが属する 1 つの workspace の rule のみです。
- **探索フェーズで破壊的操作を行わない**。手順 4/5 では `GET` または `SELECT` のみ。
  `drive-sync/sync` の発火や `drive-sync/materialize` の呼び出しはユーザーに明示的に
  指示された場合を除き行いません。
- **冪等性を最優先**。同じ指示書を 2 回貼り付けても rule が重複追記されないよう、
  手順 3 のチェックを必ず実施してください。
- 追記前にユーザー確認 (手順 7) を必ず取ること。ユーザーがプレビューせずに自動進行を
  指示した場合のみ、手順 7 を省略して構いません。
- **プレースホルダの置換漏れは絶対に許容しない**。手順 6 で `{{...}}` が残ったまま
  rule に保存されると、実行時に LLM がリテラル文字列として解釈してしまいます。

### シナリオ E: Drive ミラー検索からの仕訳提示

> **このセクションのワークスペース固有値** (追記時に d6e AI が確定):
>
> - **Drive ミラーのルート直下フォルダ ヒント**: `{{drive_root_hint}}`
> - **追記日時 (ISO 8601)**: `{{generated_at}}`
>
> ヒントが古くなった場合は、d6e 管理画面で本セクションを編集するか、本セクション全体を
> 削除して `drive-mirror-followup-prompt.md` を再度貼り付けてください。

#### トリガ条件

次のいずれかを満たすメッセージのみシナリオ E を発動します。該当しなければシナリオ
A/B/C/(D) に従い、本シナリオの指示は無視してください。

1. メッセージに `<drive_lookup_request>...</drive_lookup_request>` タグが含まれる
   (タグ内には自由文の検索意図、例: 「2025 年の AWS 利用料の領収書を探して仕訳を出して」)。
2. メッセージに `<drive_followup>...</drive_followup>` タグが含まれる
   (タグ内には直前のシナリオ E 出力 (`kind: "journal"`) に対する Drive 検索条件の修正
   指示、例: 「年度を 2024 年に変えて」)。
3. 自由文メッセージで「過去の領収書から」「Drive から」「同期したフォルダから」などの
   フレーズが含まれ、かつ添付ファイルが **無い** 場合。
   - 添付ファイルが **ある** 場合はシナリオ A を優先します (新規領収書の OCR が主目的
     のため)。
   - シナリオ A の応答内で「過去の類似仕訳を Drive から確認したい」とユーザーが続けた
     ターンは、改めて `<drive_lookup_request>` タグを付けてもらうよう促してください。

#### 利用ツールと前処理

本シナリオは共通ルールにある「シナリオ A/B/C ではツール不要」の例外として、次の
MCP ツールを能動的に使用します。

- `d6e_sql`: `drive_files` 投影テーブルの探索 (`SELECT` のみ)。
- `d6e_read_drive_file`: ヒットした行の `drive_id` を渡して `storage_file_id` を得る。
- `d6e_view_image` / `d6e_extract_file_text`: 取得した `storage_file_id` から本文・
  金額・日付などを抽出する。

最初に必ず `d6e_sql` で
`SELECT COUNT(*) FROM drive_files;` を実行し、結果が 0 件、もしくはクエリ自体が
「relation drive_files does not exist」などのエラーを返した場合は、`drive_files` 投影
テーブルがまだ存在しないということなので、シナリオ E は **発動せず** に
シナリオ A / C のいずれか妥当な方にフォールバックします。フォールバックした応答では
`warnings[]` (シナリオ A) または本文末尾 (シナリオ C) に
「Drive ミラーが未設定または未同期のため、Drive 検索はスキップしました」と日本語で
1 行残してください。

#### 探索ステップ

1. **検索意図の言語化**: メッセージから「ベンダー名」「金額帯」「年月範囲」
   「想定勘定科目」を抽出します。タグ内の自由文 → なければメッセージ全体を解析。
   検索意図がまったく特定できない場合は `status: "needs_input"` で停止し、
   `follow_up_question` に「Drive で何を探しますか? ベンダー名や年月を教えてください」と
   入れて返します。
2. **大まかな候補抽出**: 次のような `d6e_sql` を組み立てて `drive_files` を `SELECT`
   します。検索フィールドは `name`, `path`, `mime_type`, `modified_time` の順に試して
   ください。

   ```sql
   -- 例: 2025 年の AWS 関連レシート
   SELECT drive_id, path, name, mime_type, size, modified_time
   FROM drive_files
   WHERE is_folder = false
     AND name ILIKE '%aws%'
     AND modified_time >= DATE '2025-01-01'
     AND modified_time <  DATE '2026-01-01'
   ORDER BY modified_time DESC
   LIMIT 10;
   ```

   ワークスペース固有のヒント (`{{drive_root_hint}}`) を踏まえ、最初の WHERE は
   フォルダパスで絞ってから (`path ILIKE '/経費レシート/%'`) 名前で絞り込むなど、
   結果集合を小さくする工夫をしてください。

3. **候補の提示**: ヒットが多い場合 (>5 件) は上位 5 件を `path` と `modified_time` 付き
   でユーザーに提示し、どの行を採用するか確認します。ヒットが 1〜2 件なら自動採用で
   構いません (ただし `warnings` に「Drive から自動採用した行: <path>」と必ず残します)。
4. **本文の取得**: 採用した行の `drive_id` を `d6e_read_drive_file` に渡し、返ってきた
   `storage_file_id` を `d6e_view_image` (画像/PDF) または `d6e_extract_file_text`
   (Office 文書 / OCR) で読み取ります。複数行を採用する場合はそれぞれ実行します。
5. **仕訳の組み立て**: 抽出した内容を元にシナリオ A と同じ `kind: "journal"` スキーマ
   で仕訳を 1 件以上組み立てます。`warnings[]` には Drive 由来であることを示す 1 行
   (例: 「根拠書類: Drive `/経費レシート/2025/aws-2025-05.pdf`」) を **必ず** 1 行ずつ
   入れます。

#### 出力フォーマット (厳守)

本シナリオの出力は **シナリオ A と同じ `kind: "journal"` スキーマ** を使います。新しい
`kind` を導入しません。これにより既存のフロント側の `parse-journal.ts` /
`journal-result.svelte` がそのまま再利用できます。

```json
{
  "kind": "journal",
  "entries": [
    {
      "date": "2025-05-31",
      "debit_account": "通信費",
      "credit_account": "クレジットカード",
      "amount": 12450,
      "tax_amount": 1132,
      "description": "AWS 利用料 (2025-05)"
    }
  ],
  "warnings": [
    "根拠書類: Drive `/経費レシート/2025/aws-2025-05.pdf` (drive_id=1AbC...)。`d6e_read_drive_file` 経由でキャッシュ済み storage_file を読みました。"
  ]
}
```

JSON の前には 1〜2 文の日本語前置きを置きます (例:
「Drive ミラーから 2025 年の AWS 利用料明細を 1 件特定し、仕訳を生成しました。」)。コード
ブロックの後ろには何も書かないでください。

#### フォールバック / `needs_input` 規約

シナリオ E が `kind: "journal"` を返せないケースでは、シナリオ A と同じく以下のいずれかに
落とします (新しい `kind` を導入しません):

- **検索意図が不明**: シナリオ C と同じく平文の日本語マークダウンで質問し、
  ` ```json ``` ` は出力しません (Drive ヒントを示しつつ「ベンダー名や年月を
  教えてください」と促す)。
- **Drive 検索でヒットなし**: 検索条件と結果 0 件であることを `warnings` に書き、
  仕訳本体 (`entries`) はユーザーが提示した既知情報のみで暫定的に生成します。生成が
  困難な場合はシナリオ C と同じく平文応答に切り替えます。
- **`drive_files` が未存在 / 空**: 本セクション冒頭の「最初に必ず」の節に従い、
  そもそもシナリオ E を発動せずにシナリオ A / C に処理を委譲してください。

#### 安全規約 (シナリオ E 固有)

- **本文ダウンロードは必要時のみ**: 候補 SELECT の結果から実際に `d6e_read_drive_file`
  を呼ぶのは、ユーザーが採用に同意した行 (または自動採用した 1〜2 行) のみです。
  検索結果一覧を `d6e_read_drive_file` で総当たり読み取りすることは禁止です (Drive API
  の Quota を浪費し、Drive Sync のキャッシュも肥大化します)。
- **Drive 以外の外部 API を呼ばない**: 本シナリオでは freee 等の他 SaaS API を呼ばない
  でください。freee 登録は引き続きシナリオ D の責務です。
- **書き込み禁止**: `d6e_sql` の `INSERT/UPDATE/DELETE/CREATE/DROP/ALTER` は禁止。
  `SELECT` のみを使います (LLM 公開スキーマ自体が `user_data` 限定ですが、念のため)。
- **Drive 外ファイルの参照禁止**: Drive ミラー外のファイル (ローカル
  `inputFileRefs` 等) を `d6e_read_drive_file` に渡さないでください。`d6e_read_drive_file`
  は `drive_id` (Google Drive のファイル ID) のみを受け取ります。ローカル添付ファイル
  は従来通り LLM のマルチモーダル能力で直接読み取ります。
