# カスタムフロントエンドと d6e インスタンスの関係

English version: [frontend-and-instance.md](./frontend-and-instance.md)

このドキュメントは、カスタムフロントエンド・接続先の d6e インスタンス・
中央の d6e アカウントサイトという 3 者の**関係**を説明します。本リポジトリの
3 つの実装スキル（[`skills/`](../skills/README.md)）と、リファレンス実装を
詳細に解説した [`architecture.md`](./architecture.md) の概念編にあたります。

「カスタムフロントエンドとは d6e に対して何なのか」が曖昧な場合は、まず
このドキュメントを読んでください。特に、Plugin 開発ガイドから来て、
ここまでワークスペース・STF・`template.yaml` の話ばかりだった方に
向けた内容です。

## 3 つの登場人物

```
┌────────────────────────────────┐
│ カスタムフロントエンド         │   あなたが所有する普通の Web アプリ
│ (SvelteKit / Next.js / …)      │   （例: Vercel 上）— d6e のコード
│ 例: https://keiri.example.com  │   ベースやデプロイの一部ではない
└───────────┬────────────────────┘
            │ 1. ログインリダイレクト  ┌────────────────────────────────┐
            ├─────────────────────────▶│ 中央 d6e アカウントサイト      │
            │                          │ https://www.d6e.ai             │
            │                          │  アカウント・ログイン UI・     │
            │                          │  クライアント / redirect URI   │
            │                          └───────────────▲────────────────┘
            │ 2. コード交換 +                          │ トークン中継
            │    以後のすべての API 呼び出し           │
            └─────────────────────────▶┌───────────────┴────────────────┐
                                       │ d6e インスタンス               │
                                       │ ${D6E_BASE_URL}                │
                                       │ 例: https://cauchye.d6e.ai     │
                                       │ ┌────────────┐ ┌─────────────┐ │
                                       │ │ コンソール │ │ Rust API    │ │
                                       │ │ (SvelteKit)│ │ /api/v1/*   │ │
                                       │ └────────────┘ └─────────────┘ │
                                       │ ワークスペース: SQL / ファイル │
                                       │ / STF / ワークフロー / SaaS    │
                                       └────────────────────────────────┘
```

1. **カスタムフロントエンド** — あなたが構築・ホスティング・デプロイする
   独立した Web アプリです（Vercel でも自前サーバーでも可）。d6e に
   「インストール」されるものでも、インスタンスの内部で動くものでも
   なく、コードも共有しません。d6e との接点は、インスタンスの公開 API
   への HTTPS 呼び出しだけです。
2. **d6e インスタンス**（`${D6E_BASE_URL}`）— ワークスペース（テーブル・
   ファイル・STF・ワークフロー・SaaS 認証情報・チャットセッション）を
   保有するセルフホスト環境で、1 つのオリジンの背後に API とコンソールと
   PostgreSQL が同居します。フロントエンドが d6e のデータに対して行う
   操作は、すべてこのインスタンスの HTTP API を経由します。
3. **中央 d6e アカウントサイト**（[https://www.d6e.ai](https://www.d6e.ai)）—
   ユーザーアカウントが存在し、ユーザーがパスワードを入力する場所です。
   インスタンス（OAuth クライアント）と許可 redirect URI の登録簿も
   ここにあります。フロントエンドがこのサイトとシークレットを直接
   やり取りすることはなく、ログインのためにユーザーのブラウザを
   リダイレクトするだけです。

## 関係を一文で

> カスタムフロントエンドとは、中央 d6e アカウントサイトでユーザーを
> ログインさせたうえで、**特定の d6e インスタンス上の特定のワークスペース**を
> インスタンスの公開 HTTP API — 組み込みコンソールが使うのと同じ API —
> 経由で操作する、独立してデプロイされた Web アプリである。

ここからすべてを規定する 2 つの帰結が導かれます。

- **特権的な連携は存在しません。** 有効なユーザートークン付きの
  リクエストが届くまで、インスタンスはあなたのフロントエンドの存在を
  知りません。コンソールにできることはフロントエンドにもでき、
  API 経由でできないことはコンソールにもできません。
- **セキュリティ境界はインスタンスのままです。** ポリシー・ワークスペース
  メンバーシップ・SaaS 認証情報・監査ログはすべて、ユーザートークン単位で
  サーバー側で強制されます。フロントエンドが client secret・DB 接続・
  SaaS トークンを保持することはありません。

## 何がどこで動くか

| 関心事 | 動く場所 | 備考 |
|---|---|---|
| UI・ルーティング・セッション Cookie | **フロントエンド**（あなたのホスティング） | あなたがデプロイする唯一の部分 |
| ログイン画面・ユーザーアカウント | **www.d6e.ai** | ブラウザのリダイレクトのみ |
| トークン交換・リフレッシュ | **インスタンス** `/api/v1/auth/token` | インスタンスが自身の認証情報でコードを中央サイトへ中継 |
| ワークスペースデータ（SQL・ファイル・Drive ミラー） | **インスタンス** `/api/v1/*`（Rust API） | Bearer トークン + `X-Workspace-ID` |
| ワークフロー・STF・SaaS プロキシ | **インスタンス** `/api/v1/*`（Rust API） | コンソール/チャットエージェントと同じポリシー検査 |
| 自然言語実行（`execute-by-intent`）・チャットセッション | **インスタンス** `/api/*`（SvelteKit 側） | インスタンスは 1 オリジンの背後に 2 つの API 面を持つ |
| LLM 呼び出し | **インスタンス** | ワークスペースに設定されたモデルを使用。フロントエンドが送るのはメッセージであり、モデルの API キーではない |

中段の備考にある通り、1 つの `D6E_BASE_URL` オリジンが Rust API
（`/api/v1/*`）と d6e SvelteKit ルート（`/api/*`）の両方を提供します。
インスタンス前段のリバースプロキシがパスで振り分けるためで、
フロントエンドからは 1 つのホストに見えます。リクエスト/レスポンスの
正確な形は [`d6e-api-integration.md`](./d6e-api-integration.md) を
参照してください。

## 認証: ログインは 1 回、許可リストは 2 つ

完全なフロー（シーケンス図とコード付き）は
[`d6e-auth-integration` スキル](../skills/d6e-auth-integration/SKILL.md)
にあります。関係の骨格は次の通りです。

1. フロントエンドは、自アプリへ戻る `redirect_uri` を付けてブラウザを
   `https://www.d6e.ai/auth/login` へリダイレクトします。
2. ログイン後、フロントエンドのサーバーが認可コードを受け取り、
   **インスタンスの** `/api/v1/auth/token` へ POST します。インスタンスは
   *インスタンス自身の*クライアント認証情報でコードを中央サイトへ中継し、
   インスタンスの audience で署名済みのトークンペアを返します。
3. 以後のすべての API 呼び出しは、このユーザー単位の Bearer トークンを
   持ち運びます。認可の単位はユーザーの**ワークスペースメンバーシップ**で、
   「フロントエンド用アカウント」のようなものは存在しません。

交換をインスタンスが仲介するため、フロントエンドは **client secret を
一切保持しません**。その代わり、デプロイ後のコールバック URL は
**2 箇所**の許可リストへの登録が必要です（ループバック/`localhost` URL は
例外 — 任意のポート・任意のパスで登録不要。d6e ≥ v0.20.1）。

- **www.d6e.ai** 上のインスタンスのクライアント登録
  （セルフサービス: `https://www.d6e.ai/{locale}/account/franchise`）—
  ログインページがコードを発行する時に検査されます。
- インスタンスの **`ALLOWED_REDIRECT_URIS`** 環境変数 — インスタンスが
  コードを中継する時に検査されます。変更にはインスタンスの再起動が
  必要なので、インスタンス運用者と調整してください。

## Plugin との関係（と、混同しないための整理）

Plugin とカスタムフロントエンドは、**同じ API 境界線の反対側**から
d6e を拡張します。

| | **Plugin** | **カスタムフロントエンド** |
|---|---|---|
| 実体 | *ワークスペースの中身*（プロンプト・テーブル/ポリシー・STF・ワークフロー・Effect・ファイル）を詰めた `template.yaml` パッケージ | ワークスペースを*利用する*独立した Web アプリ |
| 存在する場所 | インスタンスの**中**（ワークスペース単位でインストール） | インスタンスの**外**にデプロイ |
| 実行主体 | インスタンス（QuickJS/Docker ランタイム・ワークフローエンジン・チャットエージェント） | あなたのホスティング |
| UI | 自前の UI は持たない — d6e コンソール/チャット越しに使う | それ自体が UI |
| 配布 | Install from URL / マーケットプレイス | 通常の Web デプロイ |

両者は自然に組み合わせられます。フロントエンドが依存するワークスペースの
振る舞い（テーブル・プロンプトルール・ワークフロー・STF）を Plugin として
パッケージ化すれば、新しいワークスペースを再現可能な形で用意でき、
`template.yaml` とフロントエンドのコードを同じリポジトリで配布することも
できます。本リファレンスアプリはまさにその構成です — ワークスペース側は
[`workspace-setup.md`](./workspace-setup.md) を参照してください。

Plugin 開発そのもの（STF ランタイム・instant-run・ワークフロー定義・
マーケットプレイス公開）については
[d6e-plugin-skills](https://gitlab.com/cauchye/d6e-ai/d6e-plugin-skills)
リポジトリと、その
[ローカル AI エージェント開発ガイド](https://gitlab.com/cauchye/d6e-ai/d6e-plugin-skills/-/blob/main/docs/local-ai-development.ja.md)
を参照してください。

## コンソールか、Plugin か、カスタムフロントエンドか

- **コンソールのみ** — 組み込みの d6e コンソール（チャット・データ
  ページ・ワークフロー実行）はそれだけで完結した UI です。ユーザーが
  コンソールで困らないなら、フロントエンドは不要です。
- **Plugin のみ** — 振る舞い（プロンプト・STF・ワークフロー）を
  パッケージ化して任意のワークスペースにインストール可能にします。
  利用は引き続きコンソール経由です。コンソールの UX で十分だが、
  *振る舞い*を再現可能にしたい場合に適しています。
- **Plugin + カスタムフロントエンド** — 特定のユーザーに、タスクの形に
  合わせた専用 UI（汎用チャットではなく「領収書をアップロード → 仕訳が
  出てくる」など）を、独自ドメイン・ブランディング・簡略化された
  フローで提供したい場合。フロントエンドは Plugin が用意したものを
  消費します。

## ライフサイクルまとめ

1. **ローカル開発** — 任意の `localhost` ポートで `npm run dev`。OAuth の
   ループバックは登録不要です。`D6E_BASE_URL` を稼働中のインスタンスに
   向け、実データで反復開発します。
2. **ワークスペースの用意** — コンソールで手動構築するか、Plugin
   （`template.yaml`）をインストールします。
3. **フロントエンドのデプロイ** — 静的/SSR ホスティングならどこでも
   動きます（本リファレンスは Vercel）。
4. **デプロイ後の redirect URI 登録** — www.d6e.ai *と*インスタンスの
   `ALLOWED_REDIRECT_URIS` の両方に登録し、インスタンスを再起動します。
5. **運用** — トークン・ポリシー・メンバーシップはインスタンスが
   ユーザー単位で強制します。フロントエンドはステートレスなプロキシ +
   UI であり続けます。
